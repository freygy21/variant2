# ЛР3. Тип карты и канал оплаты

Вариант: **Card**.

## Что дано

Предметные объекты, внешний API и вспомогательные типы уже подготовлены. В `app/domain/usage.py` даны заготовки общего интерфейса и двух исполнителей. Их поведение и основной метод `CardService.check()` требуется завершить самостоятельно. Сигнатуры сохранены; новые слои и выбор архитектуры не нужны.

## Задание

### Шаг 1. Реализуйте общий интерфейс и два поведения

Реализуйте абстрактный класс `CardUsageRule` и наследников `AllowedCardTypeRule(types)` и `OnlineUsageRule`.

Первое правило проверяет, входит ли `card_type` в переданный набор; иначе возвращает `CARD_TYPE_DENIED`. Пустой набор запрещает все типы. Второе запрещает `ONLINE`, если `online_enabled=False`, с кодом `CARD_ONLINE_DISABLED`; для `POS` это ограничение не действует.

Сервис должен вызывать общий `check()`. Статус и срок проверяются до этих правил.

### Шаг 2. Соберите путь вызова в `CardService.check()`

Получите карту, вызовите `availability(context.as_of)`, затем правила по порядку. Статус и срок нельзя обойти. Верните первый отказ либо `CheckResult(True)`. Не выбирайте алгоритм по конкретному классу исполнителя.

### Шаг 3. Проверьте повторное использование

Активная карта доступна; после блокировки возвращается `CARD_BLOCKED`; после разблокировки снова доступна. Старый результат не изменяется.

## Примеры и границы

- Для набора `{STANDARD}` карта `STANDARD` проходит, `VIRTUAL` получает отказ.
- `ONLINE` при `online_enabled=False` запрещён, `POS` разрешён.
- При двух отказах возвращается первый по порядку правил.
- Просроченная карта отклоняется до дополнительных правил.

Последовательности и конфигурации дополнительно проверяются в `tests/test_progression.py`. Прочитайте ожидаемый результат каждого сценария до реализации.

Все проверки открыты: `tests/test_contract.py` и `tests/test_review_contract.py`.
Описание объектов — в [REFERENCE.md](REFERENCE.md), исходные результаты тестов — в [STARTER-STATE.md](STARTER-STATE.md).
