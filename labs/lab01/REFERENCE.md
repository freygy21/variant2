# Card: справка по объектам

Здесь описаны данные и методы сервиса. Нужные изменения для ЛР1 перечислены в [TASK.md](TASK.md).
Часть методов уже реализована в заготовке, остальные добавляются по мере выполнения работ.

## Данные и поведение

`Card` хранит состояние карты и связь с клиентом и счётом. Денежный остаток хранится на счёте, а не в карте.

| Объект | Данные и назначение |
|---|---|
| `Card(card_id, customer_id, account_id, expiration_date, card_type, online_enabled=True, contactless_enabled=True)` | Карта со статусом `NEW`. Допустимые типы — `STANDARD` и `VIRTUAL`. |
| `CardContext(as_of, channel, contactless)` | Дата проверки, канал и признак бесконтактной операции. Класс уже готов. |
| `CardService` | Находит карту и проверяет возможность оплаты. |

`Card.availability(as_of) -> CheckResult` проверяет статус, затем срок действия. Дата передаётся явно; последний день срока включён. Истечение срока не меняет хранимый статус.

`CardService.check(card_id, context)` вызывает `availability(context.as_of)` перед дополнительными правилами. Их общий интерфейс — `CardUsageRule.check(card, context) -> CheckResult`. Начальные реализации: `AllowedCardTypeRule(types)` и `OnlineUsageRule`.

Хранилище, контекст, перечисления и исключения уже реализованы.

## Работа с готовым кодом

Обращение к сервису выполняется через `app/api.py`. Разрешённые файлы указаны в [TASK.md](TASK.md).
Проверки используют подготовленные данные и не зависят от работы других групп.

Функции `create`, `make`, `call` и `view` связывают готовый API с реализацией. Используемые ими функции сервисного модуля должны сохранять сигнатуры. Сам `app/api.py` не редактируйте.

До ЛР5 сборка предоставлена готовой. Нужные объекты могут создаваться в сервисном модуле; `assembly.py` менять не нужно.

## Ошибки и результаты

`DomainError` содержит код ошибки. При отказе проверки состояние объекта не должно меняться.
Ошибка переданной зависимости не заменяется успешным результатом. Конкретные коды и примеры
приведены в задании и открытых тестах.
